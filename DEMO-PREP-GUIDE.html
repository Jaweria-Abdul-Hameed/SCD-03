3. The 11-Step Data Lifecycle & RAGOps Vector Architecture [END-TO-END DATA PATH]

In RAHBAR, query execution is strictly divided into pre-retrieval validation, vector indexing, dual-rail guardrail sanitization, and structured post-generation verification. Here is the exact end-to-end trace:

[1. Client Query Input] {"question": "What is the passing CGPA?"} │ ▼ [2. Input Safety Rail (I)] (Regex & semantic check for jailbreaks; e.g. "ignore previous instructions" → Reject) │ ▼ [3. Redis Semantic Query Cache] (Checks cosine similarity against query hashes; If similarity > 0.96 → Instant 10ms Cache Hit) │ ┌───────────┴───────────┐ [Cache Hit] [Cache Miss] │ │ ▼ ▼ (Return cached JSON) [4. Dense Vector Embedding] (Ollama nomic-embed-text:latest prepends "search_query: " → 768d vector) │ ▼ [5. ChromaDB HNSW Vector Search] (Finds top-k nearest chunks in cosine space; Filters out superseded policies: where={"superseded": false}) │ ▼ [6. SQLite Raw Text & Metadata Lookup] (Fetches chunk text & attributes from chroma.sqlite3) │ ▼ [7. Relevance Floor Evaluation] (Is max cosine similarity < 0.640?) ├── YES: Abstain immediately ("The corpus does not cover...") │ (answered_from_context=false; ZERO tokens sent to LLM!) └── NO: Proceed │ ▼ [8. Retrieval Safety Rail (R)] (Scans retrieved chunks for injected prompt directives; Excludes poisoned chunks like b11 and logs audit event) │ ▼ [9. Augmented Prompt Assembly] (System instructions + Delimited <context> XML + User Question) (Computes SHA-256 hash of assembled prompt for trace verification) │ ▼ [10. LLM Inference (llama3.2:3b)] (Temperature=0.2; outputs strict JSON schema with reasoning & citations) │ ▼ [11. Citation Validation & Trace Logging] (Verifies every cited source/page was retrieved in Step 6; Emits 16-field JSONL record to /traces/traces.jsonl; Inserts into Redis cache and returns JSON response to client)
Core Viva Concept: Did We Convert Vector Chunks Back to Text?

NO! Embedding vectors are mathematically one-way, irreversible projections. You cannot take a 768-dimensional floating point vector and "invert" or "de-embed" it back into English sentences. Information theory makes this mathematically impossible because an infinite number of linguistic phrasing variations collapse into similar dense vector representations.

How ChromaDB Actually Works: Chroma is an integrated dual-layer database:

  • Vector Index (HNSW Graph): Holds only the 768-dimensional float vectors in memory and disk files to compute approximate nearest-neighbor cosine distances.
  • Document & Metadata Store (Embedded SQLite — chroma.sqlite3): Stores the original, uncompressed UTF-8 string text of each chunk, mapped by its primary key chunk_id, along with metadata (source, section, page, doc_version, superseded).

When the HNSW index finds the top 5 nearest vector IDs (e.g. ['4431bedb...', 'f15d5a0b...']), Chroma performs an internal SQL query: SELECT text, metadata FROM chunks WHERE id IN (...) and returns the raw document text to the FastAPI application.

5. The Chronological Transition Story (Phases 1 to 6) [SYSTEM EVOLUTION]

Assignment 03 transformed RAHBAR from a basic retrieval pipeline into an enterprise-grade RAGOps platform adhering to the principles outlined by Xu et al. (2026). Here is the chronological progression:

Phase 1: Corpus Curation, Defect Analysis & Pre-Chunking Verification
Implemented the 4 Pre-Chunking Gates in indexer/pipeline/verify.py to catch data defects before vectorization.

In Assignment 02, raw documents were chunked directly without upstream data validation. In Assignment 03, we introduced Batch B containing 11 documents with deliberate real-world defects. The pre-chunking pipeline enforces 4 strict gates:

  • Quality Gate: Enforces minimum text length (≥ 50 chars) and alphanumeric density (≥ 85%). Quarantined truncated doc b08.
  • Completeness Gate: Validates document metadata (title, author, date) and verifies PDF file headers/trailers. Quarantined corrupt PDF b07 and missing metadata doc b09.
  • Recency Gate: Compares edition timestamps against existing corpus records. Admitted b10 (Nov 2026 Academic Rules) and automatically marked the June 2026 edition as superseded.
  • Uniqueness Gate: Executes dual-stage deduplication: SHA-256 byte hashing catches exact duplicates (b04, b05), while embedding cosine comparison (≥ 0.94) catches near-duplicates (b06, cosine 0.9713).

Result: Out of 11 incoming documents, 6 defective documents were quarantined to corpus/quarantine/, and 5 clean documents were admitted. Running an unchanged corpus re-index scanned 15 files, skipped 15, and embedded exactly 0 chunks.

Phase 2: 3-Level Offline Evaluation Suite & Judge Calibration
Built modular evaluation in eval/run_ragops_eval.py covering Module, Component, and E2E metrics.

We structured offline evaluation across 3 distinct architectural layers:

  • Level 1 (Module): Tested embedding separation (Paraphrase cosine 0.7722 vs. Unrelated 0.4831, gap = 0.2891), chunker throughput (45.77ms/chunk), and floating-point determinism (max diff 0.00000000).
  • Level 2 (Component): Evaluated information retrieval across 21 answerable queries: Recall@3 = 0.5714, Recall@5 = 0.7143, MRR = 0.4913, nDCG@5 = 0.5460. Verified noise robustness: typo perturbations produced zero recall degradation (delta 0.0000).
  • Level 3 (End-to-End): Evaluated Faithfulness (0.8333), Abstention Precision (1.0000, 6/6), Citation Validity (1.0000, 21/21), and generation latency (p50 = 7.1s, p95 = 12.1s).
  • Judge Calibration: Evaluated both llama3.2:3b and dolphin-mistral:latest against 10 human labels. The 3B model achieved only 30% agreement due to hyper-literal keyword matching, while the 7B model achieved 90.0% agreement (9/10), proving that semantic reasoning is essential for an LLM judge.
Phase 3: Automated Canary Release Gates & Dynamic ConfigMap Decoupling
Created eval/release_gate.py to guard deployments with strict PASS/FAIL exit codes.

To prevent degraded prompts or models from reaching production, we implemented an automated release gate evaluated against an isolated candidate deployment (api-candidate:8000) reading from rahbar_corpus_candidate:

  • Passing Candidate (strict_concise_v2): Extractive structuring preserved recall (drop = 0.0000), increased faithfulness to 89.5%, and slashed p95 latency by 63.3% to 4.4s → PASS (Exit 0).
  • Degraded Candidate (bad_unconstrained_v0, top_k=1): Suffered a 33.3 percentage point recall drop → FAIL (Exit 1).
  • ConfigMap Decoupling: Stored release thresholds in configmap/rahbar-gate-config. Verified live flip: editing GATE_P95_LATENCY_MAX_MS: 500.0 failed the gate, while restoring to 45000.0 passed it immediately without rebuilding container images.
Phase 4: Production Observability, Structured Tracing & Dual Safety Rails
Engineered persistent JSONL tracing, CLI inspection tool, and dual-rail injection defenses.

Implemented production telemetry and security rails:

  • 16-Field JSONL Traces: Every request writes an atomic JSON record to /traces/traces.jsonl containing timestamps, chunk metadata, latency breakdowns, guardrail decisions, and a SHA-256 prompt hash.
  • CLI Trace Tool: Built scripts/trace_tool.py which rebuilds the prompt context, verifies the SHA-256 hash (verified=True), and displays the full execution waterfall.
  • Dual-Rail Guardrails: Input Rail (I) rejects direct jailbreaks, while Retrieval Rail (R) scans retrieved chunks for indirect prompt injection. During testing on b11, the Retrieval Rail detected 3 injection directives and safely excluded the poisoned chunk.
  • Rolling 24h Metrics: Aggregated 346 queries: top-1 similarity mean = 0.7257, p95 latency = 8,934ms, cache hit ratio = 24.8%.
Phase 5: Drift Detection & Automated Golden Set Expansion
Engineered eval/coverage_check.py to detect semantic query drift and guide golden set maintenance.

Production queries were compared against golden set questions using cosine similarity (threshold 0.70):

  • Baseline Coverage Failure: Baseline 26-question golden set covered only 59.5% (25/42) of incoming queries, failing the 70% coverage gate.
  • Topic Clustering: Clustered uncovered queries into 4 operational domains: Alumni services, Cafeteria policies, Industry internships, and International exchange.
  • Targeted Expansion: Added 6 golden questions (G27–G32) covering these clusters, lifting coverage to 85.7% (36/42) and passing the gate (Exit 0).
  • Data Drift Observation: Post-Batch B evaluation revealed that superseding June 2026 rules shifted recall from 0.7143 to 0.6190, demonstrating the importance of continuous golden set maintenance.
Phase 6: Kubernetes Single-Writer Hardening & GitOps Governance
Separated indexer and API service accounts, verified zero-downtime rollouts and instant rollbacks.

Enforced Kubernetes least privilege and deployment safety:

  • Single-Writer RBAC: indexer-sa has exclusive write access to Chroma and storage PVCs, while api-sa is strictly read-only.
  • Zero-Downtime Rollouts: Configured maxUnavailable: 0 and preStop: sleep 5 to ensure zero dropped requests during rolling updates.
  • Instant Rollback: Verified kubectl rollout undo restoring operational status in under 3.5 seconds.

6. Tooling Decision Matrix (Why X, Not Y) [ENGINEERING TRADE-OFFS]

Every architectural decision in RAHBAR was selected after evaluating concrete operational and algorithmic trade-offs:

Architectural Choice What Was Chosen (X) Alternative Rejected (Y) Concrete Engineering Justification
Data Quality Gates Pre-Chunking Verification (4 Gates) Post-Retrieval Chunk Cleaning Checking quality, completeness, recency, and uniqueness *before* chunking prevents HNSW vector graph fragmentation, eliminates wasted embedding computation, and guarantees defective chunks never enter the database.
Offline Judge Model dolphin-mistral:latest (7B) llama3.2:3b (3B) In human calibration tests, the 3B model achieved only 30% agreement due to hyper-literal keyword matching. The 7B model achieved 90.0% agreement by correctly recognizing valid semantic paraphrases and nuanced factual claims.
Release Gate Architecture Decoupled ConfigMap Thresholds Hardcoded Python Constants Storing release thresholds in configmap/rahbar-gate-config allows SREs to tighten latency or recall requirements dynamically without rebuilding or re-tagging container images.
Canary Evaluation Isolation Dedicated Collection (rahbar_corpus_candidate) In-Place Mutation of Production Store Mutating production Chroma during evaluation risks corrupting production query serving. An isolated candidate collection and separate API deployment ensure 100% test isolation.
Trace Storage Format Structured Append-Only JSONL (/traces) OpenTelemetry / Jaeger Daemon A lightweight JSONL emitter has near-zero CPU/memory overhead, requires no distributed tracing daemons, and allows deterministic SHA-256 prompt hash verification using standard CLI tools.
Prompt Injection Defense Dual-Rail (Input Rail + Retrieval Rail) System Prompt Instructions Alone LLMs frequently ignore passive prompt instructions when presented with sophisticated indirect injection attacks embedded in documents. The Retrieval Rail programmatically strips malicious directives before prompt construction.
Query Drift Detection Dense Cosine Similarity (Threshold 0.70) Lexical N-Gram / Jaccard Overlap Lexical overlap fails when users ask questions using different vocabulary (e.g. "dining hall" vs. "cafeteria"). Dense embedding similarity accurately captures semantic alignment regardless of phrasing.
Kubernetes RBAC Single-Writer indexer-sa Shared Read-Write ServiceAccount Chroma's embedded SQLite backend allows only one active writer. Granting write permissions exclusively to the indexer prevents concurrent write panics and database locking bugs.

Incident 1: Evaluator Dockerfile Import Collision (FastAPI Dependency Leak) BUILD & PACKAGING

Category 1: Pre-Chunking Verification & Data Management

Q1: Why implement pre-chunking verification instead of sanitizing chunks post-retrieval? DATA GATES

Answer: Sanitizing chunks post-retrieval is too late. Once a defective document is chunked and embedded, it fragments the HNSW vector graph, pollutes top-k retrieval results, wastes vector database memory, and risks leaking poisoned text into the LLM context. Enforcing the 4 Pre-Chunking Gates (Quality, Completeness, Recency, Uniqueness) guarantees that only clean, valid, un-superseded documents enter the indexing pipeline.

Reference: indexer/pipeline/verify.py & docs/PIPELINE.md
Q2: How does near-duplicate detection work without comparing every document O(N^2)? ALGORITHMIC

Answer: We employ a two-stage filter. First, exact duplicates are caught in O(1) time using SHA-256 byte hashing. For near-duplicates, we compute document-level semantic embeddings and query Chroma's HNSW index with a high cosine similarity threshold (0.94). This achieves approximate nearest neighbor search in O(log N) complexity rather than O(N^2) pairwise comparisons.

Reference: indexer/pipeline/verify.py (UniquenessGate)
Q3: What happened to the 6 defective documents in Batch B? CORPUS AUDIT

Answer: All 6 were quarantined to corpus/quarantine/: b04 and b05 were caught by the SHA-256 uniqueness gate (exact duplicates); b06 was caught by the semantic uniqueness gate (cosine 0.9713); b07 failed the completeness gate (corrupt PDF lacking %PDF- header and EOF trailer); b08 failed the quality gate (truncated text ending mid-sentence, < 50 chars); and b09 failed the completeness gate (missing metadata).

Reference: eval/results/verification_batch_b.json
Q4: How did you prove that re-indexing an unchanged corpus embeds zero chunks? IDEMPOTENCY

Answer: We executed an unchanged corpus re-index test (reindex-unchanged-1). Category 6: Kubernetes Architecture & Reliability

Q28: Why is Chroma a StatefulSet instead of a Deployment? STORAGE

Answer: ChromaDB relies on embedded SQLite (chroma.sqlite3) and local binary HNSW index files. SQLite requires POSIX file locking. If Chroma were a multi-pod Deployment or mounted over shared NFS, concurrent writes cause database is locked panics and silent index corruption. A StatefulSet with volumeClaimTemplates (5Gi RWO PVC) guarantees a single writer, stable DNS (chroma-0.chroma), and persistent storage that survives pod restarts.

Reference: docs/adr/0001-indexer-as-job.md & docs/ARCHITECTURE.md
Q29: Why is the Indexer a Job and not an API startup hook? ARCHITECTURE

Answer: If indexing ran at API startup: (1) Our 3 API replicas would race to index simultaneously, causing write collisions in SQLite; (2) The API's /readyz probe would fail for over 90 seconds during extraction/OCR, triggering Kubernetes restart loops; (3) API pods would need heavy PDF parsing and OCR libraries, bloating image size and baseline RAM. A decoupled Job ensures batch isolation.

Reference: docs/adr/0001-indexer-as-job.md
Q30: How do your `/healthz` and `/readyz` probes differ? PROBES

Answer: /healthz is a pure liveness probe that verifies only whether the Python process and event loop are responsive. It never checks external dependencies. If /healthz touched Chroma, a brief Chroma network blip would cause K8s to restart all 3 API pods simultaneously, causing a cascading outage. In contrast, /readyz verifies downstream connectivity: it checks Chroma, confirms the collection is non-empty (> 0 chunks), verifies Redis ping, and enforces the embedding model pin.

Reference: api/app/routes/health.py
Q31: How do Calico NetworkPolicies enforce zero-trust isolation? NETWORKING

Answer: Default-deny ingress policies are applied to all backend pods. The Web UI can only communicate with the API on port 8000. Direct network connections from UI pods to Chroma (port 8000) or Redis (port 6379) are blocked by Calico kernel iptables rules, eliminating lateral privilege escalation vectors.

Reference: k8s/base/networkpolicy.yaml
Q32: What security context flags are enforced on all container pods? SECURITY

Answer: All pods run with non-root user (runAsUser: 10001), allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, and Linux capabilities dropped (drop: ["ALL"]). Ephemeral writes are restricted to dedicated in-memory emptyDir mounts on /tmp.

Reference: k8s/base/api-deployment.yaml -> securityContext
