Executive Summary & Theoretical Basis

This production-grade system extends the RAHBAR academic advising platform to fully operationalize the RAGOps lifecycle formalised by Xu et al. (2026). Deployed on a multi-replica Kubernetes cluster with single-writer controls, the pipeline incorporates four pre-chunking verification gates, a 3-level offline evaluation suite (Module, Component, E2E), dual-rail input/retrieval prompt injection guards, semantic cache invalidation, live query coverage monitoring, and ConfigMap-driven release gates with instant rollback capabilities.

3 Part A: Data Management, Pre-Chunking Verification & Data Lake (Paper §§4.2.1–4.2.4)

In traditional RAG systems, corrupt or outdated documents are ingested into the vector store and only cause failures during retrieval or generation. RAHBAR enforces pre-chunking verification: every file must pass four independent gates before tokenization. Failing documents are immediately quarantined to /corpus/quarantine/<run_id>/ with a structured report, guaranteeing zero polluted chunks enter ChromaDB.

LLM-as-a-Judge Calibration & Selection

To prevent circular bias where the generation model judges itself, we calibrated an independent judge against 10 human-labeled answers (eval/judge_human_labels.jsonl). A small 3B judge (llama3.2:3b) exhibited hyper-literal false rejections (achieving only 30% human agreement). Upgrading the judge to dolphin-mistral:latest (7B parameter uncensored instruction model) achieved 90.0% agreement (9/10) with human annotators, correctly identifying valid paraphrased claims as faithful.

5 Part C: Change Experiment & Release Gate (Paper §4.1(d), §§4.2.5–4.2.6)

In enterprise RAGOps, changes to prompts, chunk sizes, or models must not be deployed directly to production. We engineered an isolated candidate evaluation pipeline: candidate collections and models run in isolation (rahbar_corpus_candidate, api-candidate:8000), evaluated against the production baseline via automated gate thresholds before release.

Candidate Change Formulation

We formulated a structured extractive prompt template (PROMPT_TEMPLATE=strict_concise_v2). The prompt forces the LLM to output concise, clause-grounded assertions and strict JSON key formatting, reducing token generation length while enforcing verbatim citation mapping.

Gate Threshold Specifications (gate_thresholds.yaml)

  • recall@5_max_drop_pp ≤ 0.02: Retrieval recall must not drop > 2 percentage points.
  • faithfulness_min ≥ 0.75: At least 75% of claims must be fully grounded.
  • p95_latency_max_ms ≤ 45,000 ms: p95 response time must remain ≤ 45s.
  • abstention_correctness ≥ baseline: No regression on unanswerable queries.
  • citation_validity_min ≥ 0.90: At least 90% of citations must be fully valid.

Dual-Rail Adversarial Prompt Injection Defense (Part D4)

Malicious instructions can be introduced either via user queries (direct injection) or via poisoned documents in the corpus (indirect retrieval injection). RAHBAR deploys a dual-rail defense:

  • Input Rail (I): Scans incoming queries for override markers (ignore instructions, system override). Flags query, increments Prometheus counter, and passes query as data-only.
  • Retrieval Rail (R): Scans retrieved chunks before prompt construction. When Batch B's poisoned document b11_library_fine_addendum_injected.md was retrieved, the rail detected 3 injection patterns (ignore_previous_instructions, system_override_marker, forced_approval_directive), excluded the poisoned chunk, logged a structured audit action, and prevented jailbreak.

7 Part E: Drift & Query Coverage Checking (Paper §4.1(e), §4.2.7)

Xu et al. (2026, §4.2.7) identify test coverage drift as a primary cause of silent degradation: offline test sets fail to reflect evolving production query distributions. We implemented an automated query coverage checker comparing 42 live user queries (eval/live_queries.jsonl) against our golden benchmark (eval/golden.jsonl).

Coverage Formulation & Semantic Threshold

For each live query \(q_i \in Q_{\text{live}}\), we compute the maximum cosine similarity against all golden questions: \[\text{Sim}_{\max}(q_i) = \max_{g_j \in G} \cos\left(E(q_i), E(g_j)\right)\] A query is defined as covered if \(\text{Sim}_{\max}(q_i) \ge \tau = 0.70\). The overall suite coverage is: \[\text{Coverage} = \frac{|\{q_i \in Q_{\text{live}} \mid \text{Sim}_{\max}(q_i) \ge 0.70\}|}{|Q_{\text{live}}|}\] The pipeline enforces a strict production release threshold: \(\text{Coverage} \ge 85.0\%\).

(c) Archiving Superseded Documents vs. Outright Deletion

Outright deletion of superseded documents (such as older academic prospectuses or grading rules) is dangerous in enterprise university RAG systems for three reasons: (1) Historical Cohort Governance: Students graduate under the academic rules active during their catalog enrollment year; a 2023 enrolled student is governed by the 2023 prospectus, not the 2026 revision; (2) Auditability & Traceability: Past trace records (e.g., trace bcb5f6cf) reference exact chunk IDs and document hashes. Deleting chunks breaks historical trace reproducibility, violating paper §5.1; (3) Explicit Historical Queries: When users ask "What were the admission criteria in 2023?", the retriever filters on include_old_versions: true. Archiving on PVC while setting superseded: true in vector metadata cleanly segregates modern from legacy rules without losing history.

(d) Least-Trusted Metric: Faithfulness (LLM-Judge Variance & Lexical Fallback Inflation)

Least-Trusted Metric: Faithfulness (both LLM-as-a-judge and its lexical_overlap fallback). First, LLM-judge scoring is sensitive to judge capacity and stochasticity: in eval_baseline-stochasticity_20261122T155008Z.json (llama3.2:3b), faithfulness was 0.1111 in Run 1 vs. 0.1667 in Run 2—a +0.0556 run-to-run delta despite seed=42, temperature=0.0—with only 0.30 (3/10) judge_human_agreement due to hyper-literal rejections. Switching to dolphin-mistral:latest in eval_baseline-final_20261122T161035Z.json raised faithfulness to 0.8333 (0.0 delta) and human agreement to 0.90 (9/10). Second, in-cluster runs without --llm-judge used faithfulness_method: "lexical_overlap" (≥ 0.45 content-word overlap in eval/run_ragops_eval.py), which inflated faithfulness to 1.0000 in baseline_k8s.json, eval_cm-flip-fail_20261122T161900Z.json, eval_cm-flip-pass_20261122T162326Z.json, eval_post-batch-b_20261122T163228Z.json, and even the broken eval_candidate-fail_20261122T161536Z.json (9/9 = 1.0, while rejecting terse "No" on G01 in eval_candidate-pass_20261122T161336Z.json, 0.8947). Furthermore, eval/judge_human_labels.jsonl keys labels only by question id rather than trace_id/answer text, so release gating never relies on faithfulness alone and pairs it with deterministic citation_validity, abstention_correctness, and recall@5.

(e) Hardest Paper Idea & Concrete Deviations from Xu et al. (2026)

Hardest Paper Idea: Continuous live testing (§4.2.6) and closed-loop coverage checking (§4.2.7) with multi-model online judging and strict data-store governance (§4.2.3) on local Minikube hardware. Our implementation makes four concrete deviations from the paper: (1) Batch Jobs instead of live shadow/A-B evaluation: Live queries only emit JSONL traces (api/app/services/tracing.py) and Prometheus counters (api/app/metrics.py), while 3-level evaluation runs on demand as Kubernetes Jobs (k8s/eval-job.yaml, k8s/eval-job-candidate.yaml) gating rollout to deployment/api via an isolated api-candidate Deployment; (2) Lexical fallback scorer: To avoid GPU contention on host Ollama (host.minikube.internal:11434), eval/run_ragops_eval.py defaults to lexical_overlap unless --llm-judge is passed (all six committed timestamped in-cluster eval snapshots used lexical_overlap before eval-job.yaml enabled --llm-judge); (3) Synthetic live queries: eval/coverage_check.py measures cosine coverage against 42 curated synthetic queries (eval/live_queries.jsonl) rather than live user traffic, omitting automated retrieval/generation coverage checks; (4) Code-level single-writer & verification scope: ChromaDB runs without HTTP auth (NetworkPolicy + ServiceAccount do not enforce read/write RBAC), so single-writer discipline relies on Job/CronJob vs. read-only api code (api/app/retrieval/retriever.py), and verify.py omits §4.2.2 cross-document Consistency checks.

(f) Kubernetes Object → RAGOps Responsibility Mapping & Single-Writer Enforcement

Single-Writer Mechanism: Vector-store single-writer integrity is enforced by workload + application-code separation: only batch Jobs (indexer*) and CronJob (reindex, with concurrencyPolicy: Forbid) execute write code (indexer/pipeline/store.py), whereas deployment/api and deployment/api-candidate only issue read-only collection.query(...) calls (api/app/retrieval/retriever.py) against single-replica statefulset/chroma (--workers 1). NetworkPolicy (allow-chroma) blocks ui, eval, and pvc-helper from chroma:8000, but still permits api/api-candidate egress; ServiceAccounts set automountServiceAccountToken: false for K8s API isolation and do not authenticate Chroma HTTP calls (Chroma runs without HTTP auth).
