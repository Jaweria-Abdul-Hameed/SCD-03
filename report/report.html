Executive Summary & Theoretical Basis

RAHBAR extends FAST-NUCES's academic advising RAG system to operationalize the Xu et al. (2026) RAGOps lifecycle on a hardened Minikube/Calico cluster (namespace rahbar). It integrates four pre-chunking verification gates, Data Lake archiving/rollback, a 32-question 3-level offline evaluation suite, dual-rail prompt-injection defense, 21-field JSONL tracing with Redis semantic caching, live query coverage monitoring (85.71%), and ConfigMap-driven release gates with instant rollback.

3 Part A: Data Management, Pre-Chunking Verification & Data Lake (Paper §§4.2.1–4.2.4)

To prevent corrupt, incomplete, or duplicate files from entering ChromaDB, RAHBAR enforces four pre-chunking verification gates before tokenization. Failures move to /corpus/quarantine/<run_id>/ with structured reports, while Data Lake updates, deletions, and version rollbacks operate cleanly on the corpus-data PVC.

Table 3: Four Pre-Chunking Verification Gates (verify.py)
Check Implementation & Verification Rule Quarantine Condition
Quality Extracts text via PyMuPDF/OCR. Requires ≥ 20 chars; checks replacement-char/control-char ratio (≤ 0.02) & symbol noise (≤ 0.45). 0 pages extracted, null/binary corruption, or garbled text.
Completeness Validates metadata (source, title, page_count, date/version), page match, and abrupt-cutoff / truncation scans. Missing metadata, [truncated] markers, or page mismatch.
Recency Compares version_sort_key against active Data Lake registry; archives older editions when newer versions arrive. Stale edition rejected if newer version is already active.
Uniqueness Exact SHA-256 content hash match + document embedding cosine similarity (≥ 0.94) vs. active corpus. Exact hash match OR near-duplicate cosine ≥ 0.94.

5 Part C: Change Experiment & Release Gate (Paper §4.1(d), §§4.2.5–4.2.6)

To ensure like-for-like gating without cross-environment or scorer drift, all three variants were executed inside Minikube Kubernetes Jobs against identical 32-question eval/golden.jsonl and scored by the same dolphin-mistral LLM judge (seed=42, temp=0.0), recorded in eval/results/c1_baseline_vs_candidates.json.

Passing Candidate (candidate_pass.json)

Targets isolated api-candidate:8000 and rahbar_corpus_candidate (COLLECTION_VERSION=candidate-v2, TOP_K=5) with PROMPT_TEMPLATE=strict_concise_v2, enforcing terse clause-grounded answers to cut generation tail latency while maintaining retrieval depth.

Degraded Failing Candidate (candidate_fail.json)

Applies k8s/candidate-fail-config.yaml over rahbar-candidate-config: sets TOP_K=1, PROMPT_TEMPLATE=bad_unconstrained_v0, and COLLECTION_VERSION=candidate-fail-v0, demonstrating how single-chunk retrieval and unconstrained prompting break both recall and grounding.

(c) Archiving Superseded Documents vs. Outright Deletion

Outright deletion of superseded documents (older annual reports, 2023 rules, or June 2026 handbook) breaks enterprise advising RAG for three reasons: (1) Historical Cohort Governance: Students graduate under the academic rules active in their admission cohort; archiving Undergraduate_Academic_Rules_Aug_2023.pdf and Academic_Rules_Handbook_2026.pdf preserves exact legacy rules; (2) Auditability & Traceability: Historical trace records (e.g., 21eb06c5 citing b10 v2026-11 vs. 8673c83c in traces/a2_rollback_traces.jsonl, and 8b0dbee2 in traces/d5_root_cause_trace.jsonl) bind chunk_id, document_version, and SHA-256 prompt_hash—deleting chunks breaks historical replay (Paper §5.1); (3) Historical Queries & Rollback: Setting superseded: true in Chroma while archiving to /corpus/archive/ enables include_old_versions: true queries and instant version restoration (rollback.py restored 39 active chunks of Academic_Rules_Handbook_2026.pdf).

(e) Hardest Paper Idea & Concrete Deviations from Xu et al. (2026)

Hardest Paper Idea: Continuous live testing (§4.2.6) and closed-loop coverage checking (§4.2.7) with multi-model online judging and strict data-store governance (§4.2.3) on local Minikube hardware. Concrete deviations: (1) Batch Jobs instead of live shadow/A-B evaluation: Live queries emit 21-field JSONL traces (tracing.py) and Prometheus metrics (metrics.py), while 3-level evaluation runs on demand via K8s Jobs (eval-job, eval-job-candidate) against isolated api-candidate; (2) Lexical fallback in historical Nov 22 runs: eval/run_ragops_eval.py defaults to lexical_overlap without --llm-judge (used in the six historical Nov 22 snapshots before eval-job*.yaml enabled --llm-judge dolphin-mistral for all Nov 27 runs); (3) Static live-query file: coverage_check.py evaluates 42 curated queries (eval/live_queries.jsonl) manually rather than continuously sampling production traces or computing retrieval/generation/vocabulary coverage; (4) Code-level single-writer & verification scope: Chroma runs without HTTP auth (NetworkPolicy + ServiceAccount do not enforce write RBAC), so single-writer relies on Job vs. read-only API code, and verify.py omits §4.2.2 cross-doc Consistency checks.

(f) Kubernetes Object → RAGOps Responsibility Mapping & Single-Writer Enforcement

Single-Writer Mechanism: Vector-store single-writer integrity is enforced by workload + application-code separation: only batch Jobs (indexer*) and CronJob (reindex, concurrencyPolicy: Forbid) execute write code (indexer/pipeline/store.py), whereas deployment/api and deployment/api-candidate only issue read-only collection.query(...) calls (api/app/retrieval/retriever.py) against single-replica statefulset/chroma (--workers 1). NetworkPolicy (allow-chroma) blocks ui, eval, and pvc-helper from chroma:8000 while permitting api/api-candidate egress; ServiceAccounts set automountServiceAccountToken: false for K8s API isolation rather than Chroma HTTP auth.
