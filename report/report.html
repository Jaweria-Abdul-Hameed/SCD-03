Executive Summary & Theoretical Basis

This production-grade system extends the RAHBAR academic advising platform to fully operationalize the RAGOps lifecycle formalised by Xu et al. (2026). Deployed on a multi-replica Kubernetes cluster with single-writer controls, the pipeline incorporates four pre-chunking verification gates, a 3-level offline evaluation suite (Module, Component, E2E), dual-rail input/retrieval prompt injection guards, semantic cache invalidation, live query coverage monitoring, and ConfigMap-driven release gates with instant rollback capabilities.

Dual-Rail Adversarial Prompt Injection Defense (Part D4)

Malicious instructions can be introduced either via user queries (direct injection) or via poisoned documents in the corpus (indirect retrieval injection). RAHBAR deploys a dual-rail defense:

  • Input Rail (I): Scans incoming queries for override markers (ignore instructions, system override). Flags query, increments Prometheus counter, and passes query as data-only.
  • Retrieval Rail (R): Scans retrieved chunks before prompt construction. When Batch B's poisoned document b11_library_fine_addendum_injected.md was retrieved, the rail detected 3 injection patterns (ignore_previous_instructions, system_override_marker, forced_approval_directive), excluded the poisoned chunk, logged a structured audit action, and prevented jailbreak.

7 Part E: Drift & Query Coverage Checking (Paper Â§4.1(e), Â§4.2.7)

Xu et al. (2026, Â§4.2.7) identify test coverage drift as a primary cause of silent degradation: offline test sets fail to reflect evolving production query distributions. We implemented an automated query coverage checker comparing 42 live user queries (eval/live_queries.jsonl) against our golden benchmark (eval/golden.jsonl).

Coverage Formulation & Semantic Threshold

For each live query \(q_i \in Q_{\text{live}}\), we compute the maximum cosine similarity against all golden questions: \[\text{Sim}_{\max}(q_i) = \max_{g_j \in G} \cos\left(E(q_i), E(g_j)\right)\] A query is defined as covered if \(\text{Sim}_{\max}(q_i) \ge \tau = 0.70\). The overall suite coverage is: \[\text{Coverage} = \frac{|\{q_i \in Q_{\text{live}} \mid \text{Sim}_{\max}(q_i) \ge 0.70\}|}{|Q_{\text{live}}|}\] The pipeline enforces a strict production release threshold: \(\text{Coverage} \ge 85.0\%\).

9 Part G: Comprehensive Short Answer Synthesis (Questions aâ€“f)

(a) Batch B Ingestion Defects Caught & Value of Pre-Chunking Verification

Defects Caught: Our 4 pre-chunking gates caught 6 of 11 documents in Batch B: b04 and b05 were quarantined for exact duplicate SHA-256 hashes matching b01 and b02; b06 was quarantined as a near-duplicate because its dense embedding cosine similarity was 0.9713 (≥ 0.94 threshold); b07 was quarantined under Quality due to an empty extracted page stream (corrupted PDF header); b08 was quarantined under Completeness for an abrupt cut marker ([truncated]); b09 was quarantined for missing YAML title/date frontmatter; and b10 triggered automatic archival of the June 2026 Academic Rules.
Pre-Chunking vs. Post-Retrieval Verification: Verifying documents before chunking is critical. If corrupt or duplicated documents enter the vector database, they fragment HNSW index topologies, dilute cosine density, create index bloat (amplifying storage costs), and introduce conflicting chunks into top-k retrieval. Catching defects pre-chunking guarantees that every stored vector represents an active, verified, unique policy document.

(b) Metric Divergence Scenarios & Root Cause Diagnostics

Scenario 1: High Recall@5 but Low Faithfulness. Occurs when the retriever successfully locates the correct document chunk, but the chunk contains dense, legalistic, or tabular text that exceeds the LLM's comprehension capacity, or the prompt template allows unconstrained reasoning, leading the LLM to hallucinate external knowledge instead of extracting the text verbatim. Fix: Enforce strict JSON output schemas, XML context tags, and temperature step-down.
Scenario 2: Low Recall@5 but High Faithfulness. Occurs when retrieval fails to return the ground-truth chunk (returning weakly related context with similarity below floor), but the generator correctly detects the absence of evidence and cleanly abstains (answered_from_context: false). In this case, faithfulness on grounded answers is high (or vacuous), but end-to-end task utility is poor. Fix: Tune chunk overlap and implement query rewriting.

(c) Archiving Superseded Documents vs. Outright Deletion

Outright deletion of superseded documents (such as older academic prospectuses or grading rules) is dangerous in enterprise university RAG systems for three reasons: (1) Historical Cohort Governance: Students graduate under the academic rules active during their catalog enrollment year; a 2023 enrolled student is governed by the 2023 prospectus, not the 2026 revision; (2) Auditability & Traceability: Past trace records (e.g., trace bcb5f6cf) reference exact chunk IDs and document hashes. Deleting chunks breaks historical trace reproducibility, violating paper Â§5.1; (3) Explicit Historical Queries: When users ask "What were the admission criteria in 2023?", the retriever filters on include_old_versions: true. Archiving on PVC while setting superseded: true in vector metadata cleanly segregates modern from legacy rules without losing history.

(d) Least-Trusted Metric, Failure Modes & Architectural Mitigations

Least-Trusted Metric: LLM-as-a-Judge Faithfulness.
Primary Failure Modes: LLM judges suffer from three known failure modes: (1) Hyper-literalism: Rejecting correct paraphrases as unfaithful because exact token overlap was absent (observed in llama3.2:3b which scored only 30% human agreement); (2) Self-enhancement bias: When the judge model family matches the generator, it systematically rates its own outputs higher; (3) Context window truncation: Omitting evidence details during multi-chunk synthesis.
Mitigations: (1) We calibrated dolphin-mistral:latest against 10 human-labeled answers, achieving 90% agreement; (2) We coupled LLM judge scores with deterministic lexical recall and citation verifiers; (3) Fixed random seeds (seed=42) to ensure consistent scoring across runs.

(e) Hardest Ideas from Xu et al. (2026) to Implement Locally & Engineering Compromises

Hardest Concept: Real-time feedback loop integration between live observability traces (Â§5.1) and continuous online evaluation (Â§4.2.7) on consumer hardware.
Architectural Challenges: In a production hyperscale cluster, live queries are asynchronously sampled, masked for PII, evaluated by dedicated judge fleets, and continuously piped into online dashboards. Running multiple concurrent 7B LLM instances (generation model, judge model, embedding model) alongside ChromaDB and Redis inside a local Minikube VM created memory contention and latency spikes.
Engineering Compromises: (1) We routed LLM inferences to host GPU Ollama via host.minikube.internal:11434 with serialized queueing; (2) Implemented scheduled batch evaluation via Kubernetes Jobs (eval-job) rather than continuous per-request LLM judging; (3) Capped test suite evaluation at 32 curated golden queries for release gating.

(f) Kubernetes Object Mapping: Why Cloud-Native Abstractions Fit RAGOps

Deploying RAG pipelines using bare Docker containers (or Compose) fails in production because containers lack lifecycle guarantees, health probing, and access segregation. Kubernetes objects map naturally to RAGOps stages: (1) Jobs for Ingestion: Indexing is idempotent and finite; running it as a Job prevents multiple API replicas from racing on startup; (2) StatefulSets for Vector Storage: ChromaDB requires sticky network identity and stable persistent volume attachments (data-chroma-0) to prevent HNSW index corruption; (3) Deployments with HPA for Query Serving: The API is stateless and CPU-bound; Deployments enable zero-downtime rolling updates (maxUnavailable: 0) and horizontal autoscaling; (4) ConfigMaps for Gates: Decouples evaluation thresholds from container images, enabling instant gate updates without redeployment.
